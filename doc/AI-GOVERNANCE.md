# AI-GOVERNANCE.md  
Sentinel — Authority, Structure & Operational Discipline

---

## 0. Entry Context

This document is the authoritative entry point for continuing the Sentinel project in any new context (new chat, new AI, new environment).

It assumes no prior conversation history.

Sentinel is a system-first, policy-driven website for a local property oversight institution.

It is not:
- a marketing site
- a concierge brand
- a visual experiment
- a lifestyle product

The website is an interface to an operating system.

Clarity precedes aesthetics.  
Structure precedes polish.

# 1. Governance Purpose

This document defines:

- Who may decide

- What is binding
- How drift is prevented
- How continuation occurs

It prevents:

- Role confusion
- Authority drift
- Parallel execution
- Premature branding
- Undocumented decisions

This is an operating contract.

# 2. Governance Hierarchy (Binding Order)

Authority order is strict:

1. `DECISIONS.md` — What is binding  
2. `TASK.md` — What is allowed now  
3. `STATUS.md` — What is currently true  
4. `AUDIT.md` — How compliance is verified  
5. Implementation (code / UI) — Valid only if aligned  

If implementation conflicts with documentation:
→ Documentation prevails until updated.

Undocumented behavior is invalid.

# 3. Roles & Authority

## Owner — Final Authority

- Locks decisions
- Approves overrides
- Controls identity and strategic direction
- May override any document explicitly

Lock-in requires explicit acknowledgment.

No interpretation of implied intent is permitted.

---

## Creative Director / Product Spec Authority (ChatGPT)

Role:
System architect and constraint framer.

Responsibilities:
- Define structure and hierarchy
- Frame decisions before lock-in
- Maintain cross-document coherence
- Identify drift
- Enforce discipline

Limits:
- Does not execute implementation
- Does not silently lock decisions
- Does not optimize for marketing
- Does not improvise brand beyond locked doctrine

May propose.  
Cannot bind.

---

## Technical Authority (Cloudie)

Role:
Feasibility and technical risk control.

Responsibilities:
- Validate technical feasibility
- Surface risk and inconsistency
- Protect runtime integrity

Limits:
- Does not alter meaning
- Does not change product direction
- Does not redefine structure

---

## Execution Agent (Cursor)

Role:
Precise execution only.

Responsibilities:
- Execute tasks exactly as specified
- Request clarification if ambiguous
- Reflect reality back into documentation

Limits:
- No interpretation
- No speculative improvement
- No parallel tasks
- No silent deviation

Cursor decides how, never what.

## 4A. Current Structural Correction

Owner correction locked into doctrine:

- Sentinel uses one service architecture with three usage pathways:
  1. Private Absence
  2. Active Guest Use
  3. Mixed / Undetermined Use
- Pathways change framing and operational emphasis only.
- Pathways do not change packages, SLA, emergency authority, geography, legal boundaries, or identity.
- Keyholding and cleaning are core operational capabilities inside structured oversight.
- Keyholding and cleaning must not become brand positioning.
- Execution-only cleaning/keyholding/access may exist only as subordinate support without oversight responsibility.

Implementation belongs to Task 8.

# 5. Task Discipline

## Single Active Task Rule

- Only one task may be active.
- Tasks are strictly sequential.
- No partial execution of future tasks.

If work does not map to the active task:
- Stop.
- Document.
- Escalate if required.

Parallel execution = governance violation.

---

## Completion Rule

Work is complete only if:

- `TASK.md` reflects progression
- `STATUS.md` reflects reality
- `DECISIONS.md` updated if meaning changed

If documentation does not reflect work,
the work does not exist.

---

# 6. Audit Model

Audit documents (AUDIT-*.md) define the rules and results of compliance checking per doctrine.

Audits:
- Are executed by Cursor
- Are factual
- Do not evaluate quality
- Do not propose improvements
- Surface conflicts only

If conflict is detected:
- Execution stops
- Conflict documented
- Routed to Owner

No workaround allowed.

Audits may reference code only if explicitly provided.

Missing evidence must be recorded.
Inference is prohibited.

---

# 7. Escalation Doctrine

Immediate escalation required if:

- Scope changes
- Meaning changes
- Task boundary is crossed
- Placeholder risks becoming precedent
- Documentation conflicts appear

Protocol:
1. Stop
2. Name issue clearly
3. Route to Owner

Improvisation is forbidden.

# 9. Continuation Protocol (How to Resume Correctly)

When entering project in new context:

1. Read all `/doc/*.md`
2. Identify active task
3. Confirm current position in `STATUS.md`
4. Operate strictly within `TASK.md`
5. Update documentation immediately upon change
6. Audit only when appropriate

This system favors correctness over speed.

---

# 10. Drift Control Rule

If any implementation deviates from documentation:

1. Pause execution
2. Document discrepancy
3. Escalate

No silent updates permitted.
